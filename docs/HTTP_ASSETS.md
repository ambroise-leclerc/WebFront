# HTTP asset encoding

HTTP asset negotiation and fallback apply to every frontend and to custom filesystem providers.

Application providers generated by `wf embed` and custom filesystem providers can serve
gzip resources. The core assets are identity representations; see the current inventory in
[Embedded assets](EMBEDDED_ASSETS.md). If a client does not accept gzip, the HTTP server
decodes the asset and serves identity with the decoded `Content-Length` and no
`Content-Encoding`. Encoded responses carry `Vary: Accept-Encoding`; explicit `q=0`
exclusions are respected. Duplicate mentions accept a coding if any valid mention accepts it,
regardless of their order or which field contains them: `gzip;q=0, gzip` and `gzip, gzip;q=0`
both accept gzip. Coding names use locale-independent ASCII case folding.
`x-gzip` is an alias of `gzip` in preferences and stored assets, as specified by
[RFC 9110 §8.4.1.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.4.1.3).
Alias mentions share the same explicit preference, including exclusions and duplicate merging;
pass-through retains the stored coding label.
Explicit coding mentions still override `*`. Unknown parameters are ignored;
malformed qvalues, including `q=.5` (use `q=0.5`), reject only that mention.

Decoding validates gzip headers, DEFLATE blocks, CRC32 and uncompressed sizes, including
concatenated members, with a 4 MiB default total output limit.
Any trailing bytes after the final member, including zero padding, are rejected.
Fallback decoding failures or an exceeded limit return HTTP 500. If neither the stored
coding nor identity is acceptable, or a custom provider uses an unsupported coding
(such as Brotli) the client does not accept, the server returns HTTP 406. Custom codings
can still be served directly to accepting clients.

## Validated representation cache

Each server owns a bounded LRU cache through its `RequestHandler`. It is destroyed after
server tasks have drained, with no global state, background work or extra shutdown join.
A copied handler starts with an empty cache; applications never implicitly share entries.
The server context serializes requests: a cold synchronous decode completes before another
request can miss on the same revision. There is no concurrent decode worker or in-flight table.
Moving cold decoding off the I/O thread remains [#283](https://github.com/ambroise-leclerc/WebFront/issues/283).

Keys contain the **complete compressed bytes**, rather than a pathname, borrowed pointer,
modification time, checksum alone or unvalidated ISIZE trailer. Every request still opens
and reads the provider. Changed bytes at the same path cause a new validation; identical
bytes at different paths or with the `x-gzip` alias share an entry. A custom provider needs
no revision API, but must keep its backing storage valid and stable throughout each read.
Older revisions remain eligible for LRU eviction; returning to exactly those bytes is safe.

Only successful full gzip validation creates an entry. It stores decoded content and thus
its validated length. GET reuses the content; HEAD reuses its length without copying decoded
content into the response. Each hit checks the **current** decoded output budget. Corrupt
streams and over-budget failures are never cached as successful representations. Pass-through
and 406 negotiation do not access the cache.

The default retention budget is **8 MiB per server**, allocated lazily. LRU eviction accounts
for both compressed and decoded string capacities plus their terminators, entry metadata and
two list links. Allocator bookkeeping is implementation-dependent and excluded. The fixed
cache object and counters, provider storage, request/response buffers and temporary cold
decoding allocations are outside this retention budget. Admission may temporarily construct
one additional entry before eviction, bounded by the same budget; the output limit separately
bounds cold decoded bytes. A representation too large to retain is still validated and served
under the output budget, without evicting useful entries; repeated requests decode it again.
There is no separate length-only cache for oversized HEAD responses.

Set `maxDecodedAssetCacheSize` on the buffer policy (or the sixth `CustomBuffersPolicy`
argument) to change retention. The retention budget is captured at handler construction;
the decoded output budget is read for every fallback request. Zero retention disables
caching, including HEAD metadata. Policies without this member inherit 8 MiB.
`RequestHandler::fallbackCacheStatistics()` exposes decode attempts, hits (including budget-rejected hits), entries and accounted retained bytes; read it
on the server context. The LRU lookup compares compressed bytes linearly across retained
entries; gzip pass-through remains independent of this cost. Decoder throughput and buffered
bit reads remain [#282](https://github.com/ambroise-leclerc/WebFront/issues/282).

See [gzip cache measurements](GZIP_CACHE_MEASUREMENTS.md) for cold/repeated GET and HEAD data
and the optional benchmark target.

## Fallback budget

The limit applies to the sum of decoded bytes across all gzip members, for GET and HEAD.
Gzip pass-through to an accepting client does not use this budget. A smaller budget reduces
the work and memory a fallback request can consume, but it is not an I/O-thread time limit.
Applications can override decoding and retention through their buffer policy:

```cpp
#include <webfront/WebFront.hpp>
#include <cstddef>

struct AppBuffers : webfront::http::DefaultBuffersPolicy {
    static constexpr std::size_t maxDecodedAssetSize = 1024 * 1024;
    static constexpr std::size_t maxDecodedAssetCacheSize = 2 * 1024 * 1024;
};
using App = webfront::BasicWF<webfront::NetProvider, webfront::fs::DefaultFS, AppBuffers>;
```

`CustomBuffersPolicy` also accepts the limit as its fifth template argument. Policies without
`maxDecodedAssetSize` inherit the default. Zero permits only empty decoded assets. An asset
exceeding a smaller custom budget returns 500 when identity is needed; gzip pass-through is
unchanged. Caching avoids repeated decoding; it does not bound cold decode time or provider read time.
