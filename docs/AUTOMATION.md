# Developer automation and MCP

An application that opts in with `enableAutomation` exposes a bounded native controller of its own developer window and
serves it over MCP itself, with Streamable HTTP on a loopback listener of its own
([ADR-025](adr/ADR-025-mcp-http-dans-l-application.md)). There is no other program: the application is the MCP server, and
an MCP client connects to the URL it prints. The terminal remains available in the window; the agent and the person use the
same wf dispatcher, which rejects overlapping commands. Applications that do not call `enableAutomation` register nothing and
open no listener, and automation does not compile in a distribution build.

A session ID routes operations and prevents accidental cross-session requests; it is not an authentication secret. The MCP
listener is authenticated by a separate Bearer token generated by the OS.

New to WebFront, or an agent about to write an application? Start with [developing with an agent](DEVELOPING_WITH_AGENTS.md):
the model (C++ with a TypeScript/TSX interface in `ui/`), the development loop and the MCP form of each `wf` command.
This page is the reference.

For testing a consumer's own page through CTest, see [consumer testing](CONSUMER_TESTING.md).
That independent API is available in this tree; MCP is unnecessary for CI to run Jasmine.

## Enabling automation

An application that wants to be driven opts in explicitly; it keeps its callbacks, and check/build/test/preview/inspect/
interact run in **its** window. It must have called `bootstrap("developer")` (the developer environment is hosted in its
page), and it needs an environment with automation API v1 (0.6.3 or later; the setup operations `init`, `create`, `install`,
`restore` and `embed` need 0.6.4, `call` needs 0.6.6). The environment the library pins has all of them.

```cpp
#include <webfront/automation/Enable.hpp>

webfront::NativeApp app{project};
app.bootstrap("developer");
app.cppFunction("bf.render", render);                       // stays available to the previewed page
auto automation = webfront::automation::enableAutomation(app, {.grants = {"check", "build", "inspect", "interact"}});
app.show(automation->launchPage());                         // the single-use claim selects this window
automation->close();                                        // revokes the session, closes the listener, removes the files
app.shutdown();
```

The call prints one line on stderr (disable it with `announce = false`), and the window's terminal shows it too:

```text
WebFront MCP (grants: check, build, inspect, interact): http://127.0.0.1:PORT/mcp - client configuration: <private directory>/mcp.json
```

`automation->mcpUrl()`, `automation->clientConfiguration()` and `automation->directory()` give the same information to the
code, and `automation->windowTitle(base)` returns a title marked as shared. Nothing is registered unless `enableAutomation` is
called, and the grants and project are fixed there by the native owner: the agent, the page and the project manifest cannot
change them.

| Option | Default | Meaning |
| --- | --- | --- |
| `grants` | none | The granted operations: `check`, `build`, `test`, `preview`, `inspect`, `interact` (click/fill), `call`, `packages` (`list`, `why`, `info`), the setup grants `init`, `create`, `install`, `restore`, `embed`, and `state` for the `webfront.state.*` tools that read the running application. None leaves only session discovery. |
| `callbacks` | none | The application callbacks `call` may invoke, by exact name (see below). |
| `mcpPort` | 0 | The port of the listener; 0 lets the OS choose. A chosen port is never replaced: when it is taken the activation throws a `std::system_error` that names the address, the port and the cause. |
| `mcpToken` | absent | An application-supplied Bearer token, retained across launches if the application supplies the same value. Absent selects a fresh random token per session. Use a long random secret outside the project. |
| `disableMcpAuthentication` | false | Explicitly allow local clients without a Bearer token. Cannot be combined with `mcpToken`. |
| `directory` | a new directory named after the session in the discovery directory | A new private directory outside the project for `mcp.json`. |
| `discovery` | the per-user sessions directory | Where the record goes (tests use their own). |
| `timeout` | 120 s | The native deadline of one operation. |
| `startupTimeout` | 120 s | How long the window may take to claim the session. |
| `closeGrace` | 5 s | How long a revoked window may take to close before `onUnresponsive`. |
| `onUnresponsive` | ends the process with status 72 | What to do with a window that did not close. |

For a client configured once, set `mcpPort` to a fixed nonzero port and supply the same `mcpToken` on every launch, for example from a private environment variable read by the application. Copy the URL and Authorization header from the first `mcp.json` into the client's **user** configuration, outside the project. Start the application before connecting; retry after starting it if the connection is refused. Rotate the token by changing the application-supplied value and updating the client. A second instance can use the default options; a second listener on the chosen port fails explicitly.

```cpp
const char* token = std::getenv("MY_APP_MCP_TOKEN");
if (!token || !*token)
    throw std::runtime_error("Set MY_APP_MCP_TOKEN to a private random token");
auto automation = webfront::automation::enableAutomation(
    app, {.grants = {"check", "build"}, .mcpPort = 19002, .mcpToken = std::string{token}});
```

The application includes `<cstdlib>`, `<stdexcept>` and `<string>` for this example; MSVC reports `std::getenv` as deprecated (C4996), so use `_dupenv_s` or define `_CRT_SECURE_NO_WARNINGS` there. A configured token must be 32–1024 visible ASCII characters without spaces; length alone does not guarantee randomness. To opt in to an unauthenticated listener instead, use `.disableMcpAuthentication = true` and omit `mcpToken`; its client configuration has no Authorization header. In that mode any Authorization header, including an incorrect Bearer, is ignored.

The startup banner warns when authentication is disabled. It appears on stderr and, once the window connects, in the developer terminal. With `announce = false` there is no stderr warning; the terminal still receives the banner when it connects, and `automation->banner()` still returns it.

These options are for trusted development environments. A different local user can occupy the fixed port while the application is stopped and receive a durable Bearer sent by the client, then reuse it when the application starts. Without authentication, any local process that reaches the listener can exercise its grants. A fake server can also send misleading responses. Loopback, strict Host, Origin and Sec-Fetch checks remain enabled in both modes; they do not authenticate the server to the client.

After a crash or forced termination, the private `mcp.json` can remain on disk with the durable token. Session discovery prunes known files in default session directories when it detects a dead process, but cleanup can be delayed or fail; an explicitly supplied `directory` is not pruned by discovery. Inspect and remove stale private files as needed, and rotate a token if it may have been exposed.

All executable operations are denied unless granted. The setup grants write the manifest, the lock, the cache, a new starter
directory or the generated provider header; grant them only for a project whose registry you trust. `install` and `restore`
use the registry already configured by the owner, the manifest or the default; the operation cannot choose another one.
There is no operation for a shell, JavaScript evaluation, arbitrary callbacks, `wf run`, `exec` or arbitrary native file
reads/writes: an agent edits project files through its separately authorized workspace tools, then asks WebFront to verify
them.

A lost WebSocket does not prove the native window is gone (a navigation or a broken connection can leave it open, with
`show()` still blocked): the record and the listener are withdrawn at once, but the grace still runs until the application
calls `close()` after `show()` returns, so call it promptly. A window that never claims the session (`startupTimeout`) is
revoked the same way, since no operation exists for the deadline to expire. The native deadline of an operation revokes the
session and asks the window to close. A renderer stuck in a loop never runs that request, and `show()` cannot be interrupted
from another thread: after `closeGrace` the listener, the files and the record are removed and `onUnresponsive` is called,
which by default ends the process with status 72. An application that prefers another way to stop sets `onUnresponsive`.

Automation does not exist in a distribution build: `Enable.hpp` and `McpHttp.hpp` stop the compilation with an `#error` when
`WEBFRONT_DISTRIBUTION` is 1, on purpose, so that no listener can ship. Gating the call alone is not enough: put the
`#include <webfront/automation/Enable.hpp>`, the `enableAutomation` call and any code that uses automation under the same
condition, for example:

```cpp
#if !WEBFRONT_DISTRIBUTION
#include <webfront/automation/Enable.hpp>
#endif
// ...
#if !WEBFRONT_DISTRIBUTION
    auto automation = webfront::automation::enableAutomation(app, {.grants = {"check", "test"}});
#endif
```

### Calling the application's own callbacks

Testing the behavior of the application, not only its interface, needs its C++ callbacks. They are never exported by
default: the owner names the ones an agent may call and grants `call`.

```cpp
auto automation = webfront::automation::enableAutomation(
    app, {.grants = {"check", "build", "preview", "inspect", "interact", "call"}, .callbacks = {"bf.render"}});
```

The agent then starts `call` with `{"callback": "bf.render", "value": "glider"}`.

`call` takes the `callback` name and at most one string `value`; its result is `data: {callback, result}`, where `result` is a
string, a number, a boolean, `null` or a list of at most 1000 of those (typed arrays included), and at most 40,000 bytes once serialized; a larger answer fails the run with that reason instead of succeeding without its value. Anything else, a
`webfront.*` name, a name that is not in the list (matched exactly, never as a pattern) and a session without the grant are
refused natively and audited, whatever the page or the agent asks; the list cannot come from the project manifest or from
the agent. The names are visible in the session (`callbacks`), in the discovery record and in the terminal notice. The callback runs in
the application's own process with the application's authority: allow-list only callbacks that are safe to trigger. An
environment older than 0.6.6 cannot run `call`, and the native owner refuses the grant rather than ignore it. `call` is an
operation of `webfront.start`, not one MCP tool per callback, so the tool list stays at four. A callback in progress cannot be interrupted: cancelling a `call` keeps the run, the session's lock and the native deadline until the callback returns, then reports it cancelled (its effect is not undone); a callback that never returns ends with the native deadline, which revokes the session.

## The MCP listener

- **Address.** The listener binds `127.0.0.1` only, on a port the OS chooses, distinct from the page's port and never
  served with TLS, whatever the application's own address and TLS listener. `mcpPort` chooses a port; a chosen port is never
  replaced: when it is taken the activation throws a `std::system_error` that names the address, the port and the cause.
  Each instance has its own URL, so several applications run side by side and the agent picks one by its URL.
- **Token.** By default every request carries `Authorization: Bearer <token>`, a 256-bit value from the OS. Before parsing the
  body, the listener compares equal-length tokens in constant time and rejects a length mismatch immediately; a failed check gets
  401 with `WWW-Authenticate: Bearer` (no OAuth server is announced). The token lives as
  long as the session by default: closing it, a deadline or a lost window closes the listener and removes the file. A supplied
  `mcpToken` remains valid across launches until the application changes it; authentication can be explicitly disabled.
- **Client configuration.** `mcp.json` (mode 0600 in a 0700 directory on POSIX, owner-only ACL on Windows) holds the URL and
  the header, ready for a client that takes a configuration file (`claude --mcp-config PATH/mcp.json`). The token appears in
  no page, URL, command line, log, banner or discovery record. Never copy it into the project, its `.mcp.json` included: the
  developer file bridge can read the project.
- **Web pages.** A request whose `Host` is not exactly `127.0.0.1:PORT` or `localhost:PORT` gets 421 (DNS rebinding); any
  `Origin`, the application's own included, or any `Sec-Fetch-*` header gets 403; a body that is not `application/json` gets
  415, and a CORS preflight gets 405 without any `Access-Control-*` header. Only `/mcp` is served: every other path, the
  page's files and the OAuth discovery paths included, is 404.
- **Protocol.** MCP 2025-11-25 Streamable HTTP, reduced: `POST /mcp` with one JSON-RPC message (a batch is refused),
  answered with `application/json`, never a server stream (`GET` is 405); `Accept` must include `application/json`. A
  notification or a client response gets 202. `initialize` assigns `Mcp-Session-Id`, which routes and does not authenticate;
  without it other requests get 400, an unknown or terminated one 404, and `DELETE /mcp` terminates the MCP session only,
  not the window. 16 MCP sessions at most, the least recently used evicted. `MCP-Protocol-Version`, when sent, must be
  2025-11-25 (400 otherwise). The body is bounded by `Content-Length` to 60,000 bytes (413), chunked bodies get 501, an
  unannounced length 411, and `Expect: 100-continue` is answered once the headers are accepted, never before a refusal.
- **Admission.** At most 64 unauthenticated peers, oldest evicted, each with two seconds
  to send its headers and body; 32 workers for authenticated requests, which silent peers never hold; 30 seconds to send an
  answer. Each connection carries one request (`Connection: close`).


Listening, accepted and client sockets are non-inheritable; POSIX closes them on exec. The application must be running
before a client connects: an MCP client cannot start it as it starts a stdio server. An agent with a shell starts the
application, then waits for its `mcp.json` or its discovery record.

## Discovering running applications

An application that enabled automation publishes `<session>.json` in a private per-user directory: `%LOCALAPPDATA%\WebFront\sessions`
on Windows, `~/Library/Application Support/WebFront/sessions` on macOS, `$XDG_STATE_HOME/webfront/sessions` or
`~/.local/state/webfront/sessions` elsewhere (`discovery` overrides it). On POSIX it must be owned by the user and closed to
others, otherwise it is not read. A missing directory is created private (0700); an existing one that others can read is
refused and left untouched, and `enableAutomation` throws, so that an application never believes it is listed when it is not.

The record has the project, grants, allow-listed callbacks, process identifier, API version, the private directory
(`endpoint`), the MCP URL (`mcp`) and the path of the client configuration (`configuration`); **never the token**, which
stays in `mcp.json`: reading a record does not let anyone operate the session. With hundreds of instances, each has its own
record and private directory, named after its session identifier (OS entropy), and its own port. The record and the
directory are removed on closure (`close()`), and by the unresponsive-window path. An application that wants them removed on
SIGINT/SIGTERM ends `show()` on those signals with `app.requestClose()`, then calls `close()`; after a forced end, the next
activation removes the records whose process is gone, with the private directory named after them. A recycled process
identifier can keep a dead record for a while.

Automation is also visible to the person at the window: once connected, the terminal prints the grants, the callbacks and
the URL in yellow, `wf help` ends with an `Automation:` line while it lasts, and `automation->windowTitle(base)` marks the
title. `wf create` writes an `AGENTS.md` beside the starter's sources that tells an agent how to connect, and the errors that
ask for a package (`wf check` without typescript, `wf test` without jasmine-core) name the `install` operation.

## MCP profile and results

The server supports protocol revision **2025-11-25**, initialization (with short `instructions`), ping and tools, over
Streamable HTTP. It advertises
no prompts, resources, sampling, logging or experimental task capability. A client requesting
another revision receives the supported revision and must decide whether it can continue, as
specified by [MCP version negotiation](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle#version-negotiation).
It should disconnect if it does not support the offered revision; the server does not silently
claim support for the client's unknown version.
Tool results include both `structuredContent` and its JSON spelling as text.

| Tool | Arguments | Result |
| --- | --- | --- |
| `webfront.session` | `{}` | API version, session ID, canonical project, state, native grants, failure reason and bounded audit metadata. |
| `webfront.start` | `{session, operation, arguments?}` | A new run ID and initial state, returned immediately. |
| `webfront.result` | `{session, runId}` | Run state, bounded streamed output and final result. |
| `webfront.cancel` | `{session, runId}` | Cooperative cancellation request and current state. |
| `webfront.state.*` (ten tools) | `{session, ...}` | With the `state` grant only: the inspectors' reads, answered at once (see [Reading the application's state](#reading-the-applications-state)). |

Operations and their arguments:

| Operation | Arguments | Grant |
| --- | --- | --- |
| `check` | `{}` | `check` |
| `build`, `preview` | `{entry?}` | Operation's own grant |
| `test` | `{pattern?}` | `test` |
| `inspect` | `{}` | `inspect` |
| `init` | `{name?}` | `init` |
| `create` | `{starter, directory?}` | `create` |
| `install` | `{package?}` (one `name[@range]`; none installs the locked graph) | `install` |
| `restore` | `{}` | `restore` |
| `embed` | `{provider}` or `{entry, output}` | `embed` |
| `click` | `{pageId, elementId}` | `interact` |
| `fill` | `{pageId, elementId, value}` | `interact` |
| `call` | `{callback, value?}` | `call` |
| `list` | `{}` (the graph of `wf list --tree`) | `packages` |
| `why`, `info` | `{package}` | `packages` |

`list`, `why` and `info` read the lock, without network or write, and answer the text of the terminal commands. They run in
environment 1.2.1 or later: with an older one, the native owner refuses the `packages` grant rather than ignore it.

### Reading the application's state

The `state` grant adds ten tools, `webfront.state.limits`, `functions`, `jsFunctions`, `browsers`, `watches`, `children`,
`changes`, `value`, `fold` and `reset`: the reads of the [inspectors](DEVELOPER_ENVIRONMENT.md) of the developer
environment (ADR-027, section 10), for an agent that would otherwise need a screenshot. Without the grant, `tools/list`
does not name them and calling one is an unknown tool.

- **Reads only.** The write of the inspectors (`webfront.inspector.write`) has no tool, whatever the application made
  writable for its panel: giving it to an agent would need a grant and a decision of its own. `fold` and `reset` change
  only the memory these reads keep of a watch, never the application nor what a panel shows.
- **Answered natively, at once.** They take no run and do not need the developer window: they answer while an operation
  runs and before the window is ready, and are refused once the session is closed. A read of a watch runs where a page's
  would (on the server thread, then on the watch's executor) and its tool call waits for it, ten seconds at most
  (`webfront.inspector.unavailable` past that).
- **Same bounds, same answers.** Each tool calls the code of the `webfront.inspector.*` function of the same name with
  the same budget: pages of 200 rows by default and 1 000 at most, passes of differences by pages, a whole value by
  fragments of one identified snapshot (16 MiB at most), 10 000 nodes kept per watch. The tuples become JSON objects and the
  flags become booleans; JSON escaping can make an answer longer than `responseBudget`, which bounds what is read, and a
  byte sequence that is not UTF-8 is replaced by U+FFFD.
- **One memory per application.** The reads have their own memory of each watch, distinct from every panel's and shared
  by the MCP clients of the session: two agents unfolding the same watch at once see each other's revisions.
- **Access by the grant, not by the view.** The inspectors answer a page only when it is a proven view of the
  application; these tools answer the authenticated MCP client of a session whose owner granted `state`. The grant shows
  the content of every watch and the last error of every function: give it for an application whose state you accept to
  show to the agent. Reading the functions opens the timing window of the calls, as a panel does.
- **Development only.** The tools need `bootstrap("developer")`: without it, enabling automation with the `state` grant
  throws `std::invalid_argument`. Neither automation nor the inspectors exist in a distribution build.

A refusal is a tool error whose `code` is the inspectors': `webfront.inspector.unknown`, `webfront.inspector.stale`,
`webfront.inspector.limit` or `webfront.inspector.unavailable`; an argument of the wrong type or out of its bounds is
`invalid_arguments`. A refused call is audited, a read is not: polling would evict the decisions the audit keeps.
[Developing with an agent](DEVELOPING_WITH_AGENTS.md#reading-the-running-application-webfrontstate) has the arguments of
each tool and the sequence that reads a watch.

`name`, `starter`, `package` and `provider` refuse a leading `-`, a backslash and spaces; `directory` and `output` must be
project-relative paths: `create` never replaces an existing directory (`wf` refuses it), while `embed` **replaces** its output header, as
regeneration requires. `embed` needs a provider, or an entry together with an output, never both.
Unknown arguments, wrong sessions, unsupported commands and option-like entry/pattern strings
are refused natively. Entries accept manifest labels (including `app:debug` and `app..debug`);
entry paths must be project-relative. A queued/running operation blocks
another native start. A terminal command already active in the page causes an explicit busy
failure instead of interleaving mutations. A `wf run` alias passes ownership to its resolved
command; module scripts retain their lease through execution and publication.
Interrupting a terminal command lets worker cancellation finish, then
returns control within 2.5 seconds if its Promise stalls, while retaining the lease until all
underlying and nested work actually settles. New operations remain busy during that interval;
reload or close a permanently stuck environment to stop it. `wf test` finishes
its bounded cancellation/cleanup before releasing ownership. A human `wf dev` owns the lease only
while compiling/publishing, including when launched through `wf run` aliases, so agents can use
the window while it waits for edits. The window displays the agent operation and a stop button.

Poll the run ID until its state is `succeeded`, `failed`, `cancelled`, `timeout` or `disconnected`. A `timeout` revokes the
session at once, listener included, so the client may get a refused connection instead of reading that last state: it
then stops polling and reports the outcome as unknown, without starting the mutation again.
Exit code 130 means `cancelled` only after a native cancel request or an authenticated page
report of an actual local abort; an unrequested script exit 130 is `failed`.
The final `result` contains `{exitCode, output, report}`; top-level `output` becomes that final
bounded output instead of the progress tail. Jasmine supplies `report`, while compiler
errors may also provide a bounded `diagnostics` array with message, source file and one-based
line/column. Inspection and actions return `data`. No terminal text parsing is needed to determine
success or locate the structured diagnostics. Output is bounded in memory and on the bridge;
`truncated` records a cut. Only the latest 64 runs are retained in process memory. An expired ID
is reported explicitly and is never silently re-executed.

`runNonInteractive` keeps its full returned output by default. Automation explicitly requests a
16,000 UTF-16-unit rolling tail; progress exposes its latest 2,048 units. A noisy command therefore
keeps fresh progress and its final summary. Serialization may reduce the tail further to fit the
bridge byte limit, with `truncated: true`; it does not replace the tail with an old prefix.

`notifications/cancelled` refers to an MCP request. Start requests finish immediately, so those
notifications cannot cancel a later background operation; use `webfront.cancel` with its run ID.
Cancellation is cooperative and cannot undo committed publications or effects in page code.
A timed-out renderer is never reused for another operation. Do not retry a mutation blindly
after a lost response; inspect its run state or report the uncertainty.

Preview inspection is limited to the local developer preview, visible elements with explicit IDs,
bounded text/labels and observed error/rejection events. It omits form values and full HTML.
Click accepts buttons, checkboxes and radio/submit controls; fill accepts ordinary text/number
fields, excluding passwords and file inputs. Actions require the inspected page revision and are
refused after navigation or while loading. Failed navigations cancel provisional loading before
the previous document can be inspected again, with a fresh revision. A navigation still pending
after 30 seconds is stopped; a replacement document already complete can also be recognized without
its load event. Inaccessible or unauthorized documents remain refused. They are synthetic DOM interactions, not a guarantee
of browser-trusted input. Captures, arbitrary selectors and full accessibility trees are deferred
because they broaden disclosure and require engine-specific qualification.

## Security boundary

Enabling automation grants the client authority over the application's trusted project, within the grants its owner fixed.
The native controller checks its grant on every start. `enableAutomation` generates a separate 256-bit
single-use window claim and passes it in the frontend URL fragment, which is not sent in HTTP
requests. The bootstrap removes the fragment from browser history before submitting its claim.
Only that claim selects the browser and releases its page key; an earlier WebSocket connection
receives no key and cannot consume the claim. The server checks WebSocket Origin against its
content policy, but does not use Host as a window identity, and native local clients can forge
Origin. Window selection therefore depends on the launch claim, not those headers or connection
order. Preview/test frames opening their own WebSocket are refused by connection identity.
Do not disclose the launch URL or its fragment; hostile same-user processes are outside this boundary.
Callback packets carry HMAC-SHA-256 proofs over a monotonic counter, method and
UTF-8 length-delimited arguments; replies are also authenticated and exact replays are refused.
The native counter accepts any strictly greater authenticated sequence. Gaps are permitted because
a local encoding/bridge failure can consume a JavaScript sequence without reaching C++; rejected
proofs do not advance the native counter. Replays and delayed older calls remain refused. The next
valid signed poll or failure report can therefore recover after a dropped call without sharing a new secret.
The bootstrap key is imported as a non-extractable WebCrypto key and its injection script removes
itself from the DOM before yielding. Later callback packets do not contain that reusable secret.
The native implementation is checked against [RFC 4231 vectors](https://www.rfc-editor.org/rfc/rfc4231).
This prevents reusing a credential observed on the callback wire. It does **not** turn same-origin
preview/test frames into isolated security principals: project code can still alter the parent's
DOM and JavaScript runtime, influence tool execution, or deny service. Trusted project code remains
a precondition; this is not a sandbox or a guarantee of trustworthy results from a hostile page.
Session identifiers are not credentials. Input is limited to 60,000 UTF-8 bytes and JSON depth 32,
with duplicate keys refused. Browser reads/writes still use the existing developer store's path
and transactional-publication checks. Untrusted project text cannot modify the native grant list.

Build/check/test/preview execute toolchain or project code. Authorized page code and C++ callbacks
retain their application authority. The manifest, origin checks, the MCP token and native grant
list do not sandbox that code against the host, stop a malicious same-user process, or prevent
an authorized agent from choosing a harmful action after prompt injection. Treat diagnostics,
logs, page labels and results as untrusted data. Use a dedicated OS/CI environment with secrets
removed and externally controlled network access for untrusted repositories.

Inherited process environment is not automatically sanitized: launch the application with the environment and secrets
appropriate to the project. Inspection limits and omission of form
values are data minimization, not a confidentiality guarantee; page text and diagnostics can still
contain secrets. Run results and the last 64 native start-authorization decisions are kept in memory,
not automatically written to disk. Audit entries carry the actual operation and the assigned run ID
(empty for a denial before allocation), and omit arguments/output. Busy, not-ready, malformed requests with valid session authority
and lifecycle completions do not evict those decisions. Retention,
access to client-side transcripts and secret expurgation remain the caller's responsibility.
The loopback MCP listener is decided by [ADR-025](adr/ADR-025-mcp-http-dans-l-application.md); its token protects it
from other users and web pages, not from a process of the same user, which can read `mcp.json`.
Remote/multi-user access (including MCP over HTTPS), arbitrary uninstrumented window discovery and physical device
control need their own reviewed authorization/isolation design.

## Validation

`AutomationMcpHttpTests.cpp` covers the listener: screening of Host, Origin, Sec-Fetch, path, method, token, media types and
lengths; MCP sessions, revisions, batches, notifications and eviction; real sockets with refusals read before a reset,
`Expect: 100-continue`, silent peers, a taken port and revocation; two activations side by side and the cleanup of a vanished
instance. The other unit tests cover native grants, cross-session rejection, path/option refusal, cancellation races,
deadline revocation, the MCP lifecycle and identifiers, and hostile JSON. `AutomationAbsentFromDistribution` checks that
`Enable.hpp` does not compile with `WEBFRONT_DISTRIBUTION`. Browser Jasmine specs cover shared dispatch arbitration and the
runner.

The window regressions drive `automation_host`, a test application that calls `enableAutomation`, through its URL with
Python's standard library HTTP client:

- `AutomationMcpWindow`: structured errors, file correction, check/build/test, preview inspection and actions, cross-frame
  rejection, a second client sharing the session and cancelling the first one's run, a project set up from nothing
  (`create`, `init`, `install`, `restore`, `embed`), and the withdrawal of the listener, record and directory when the window closes.
- `AutomationMcpWatchdog`: a real renderer blocked inside a test-archive operation body, without loading Jasmine to provoke
  the hang. It exercises the production signed callback and runner, the native two-second deadline, the five-second close
  grace and the withdrawal of the listener, record and directory; a relaunch on the same directory then checks its reuse and
  Unicode failure reporting. It delays bootstrap by three seconds to verify that the operation deadline starts after startup.
- `AutomationConsumerWindow`: two applications side by side, each driven through its own URL: refusals of web pages,
  rebinding names and the other instance's token, grants, check, build, preview, click, the application's own allow-listed
  callback, and cleanup.

They are registered when a Python interpreter and an embedded test engine are available; without xvfb-run on Linux only these
optional window tests are skipped with a warning. The mandatory Jasmine, developer and driver browser coverage still requires
a display runner and configuration fails if it is unavailable.

The maintained [official SDK regression](../test/tools/AutomationSdkClient.py) uses `mcp==2.3.0` in a separate test
environment, over Streamable HTTP with the token of `mcp.json`. It checks initialization, instructions, catalogue,
structured results, a refused operation, a real build and a second connection after the first one terminated its MCP
session. Configure registers `AutomationSdkWindow` when the selected Python already has that exact SDK installed; no SDK or
package is installed by configure or by a test. This is tested interop, not a claim of compliance with every MCP client.

### Optional local-model qualification

`test/tools/AutomationModelBenchmark.py` is a small MCP host for an already running local Ollama
model, connected to the MCP URL of the test application. It does not install or download a model, contact a public server, or grant arbitrary shell
or filesystem access. It projects the trusted MCP catalogue into function calls and separately
permits reading/writing only the generated fixture's `main.ts`. Two tasks ask the model to fix a
type error or a failing test. The harness then independently runs check/tests, records successes
and attempts per model, latency, prompt/generated token counts and the host's measured catalogue
token delta. It measures the catalogue with/without tools using identical baseline messages;
that delta is host/model-specific, not a universal tokenizer estimate.

Run it with the same host/driver/environment/provision/registry/fixture/work options as
`AutomationClient.py` (`--host` is the `automation_host` test application of a browser test build), plus `--model INSTALLED_MODEL --report results.json`. Repeat `--model` to
compare model classes; `--repeat` defaults to 3 and `--turns` to 24. `--ollama-url` defaults to
`http://127.0.0.1:11434/api/chat`; only loopback HTTP endpoints are accepted and redirects are refused.
The synthetic source produced by a model is still executable project code: use an isolated
environment with no secrets for unfamiliar models. Results are not a general safety or success
guarantee, and an unavailable model is never counted as a passing experiment.

The host follows the [Ollama tool-calling protocol](https://docs.ollama.com/capabilities/tool-calling)
and [chat token counters](https://docs.ollama.com/api/chat), consulted on 2026-10-28.

The [2026-10-29 local-model qualification](validation/automation-models-2026-10-29.md) records
five installed models tested through a separate LM Studio measurement adapter: Devstral Small 2,
Qwen 3.8, Muse Glimmer, Flint and Nemotron Cascade 2. All 30 final sources passed independent host
check/tests; 29 model conversations themselves observed both operations succeed. The report includes
per-task data, catalogue/token costs, recovered refusals, the Flint response-limit case and native
exit-status validation. It was measured with the former stdio launcher, before ADR-025; the catalogue and the operations
are the same. This is measured evidence for that setup, not a supported LM Studio mode
of the maintained Ollama benchmark or a general success guarantee.
